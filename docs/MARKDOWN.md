# Markdown rendering contract

The UI uses the official [swiftlang/swift-markdown](https://github.com/swiftlang/swift-markdown) parser, pinned exactly to [0.9.0](https://github.com/swiftlang/swift-markdown/releases/tag/0.9.0). Its CommonMark/GFM AST is adapted into public Sendable value types (`MarkdownDocumentModel`, `MarkdownBlock`, `MarkdownInline`) before presentation. This is not a regular-expression Markdown parser. `Package.resolved` records the parser and swift-cmark revisions. Initial package resolution needs network access; rendered documents do not.

`ClaudeMarkdownView` accepts a source string or a prepared document model and a separate `ClaudeMarkdownTheme`. Assistant messages use the existing 20pt Newsreader substitute. Artifact paragraphs use a 17pt system body style under the existing title/section UI. Live October 8 Claude references now establish serif bold headings, a quote left rule, blue inline code, a bordered 24pt code card with language/copy/expand header, and a rounded table with horizontal row dividers. Metrics remain approximate because the bundled serif is a substitute. Semantic correctness is independent of visual fidelity.

Supported AST presentation includes six heading levels, strong/emphasis combinations, strikethrough, inline code, paragraphs/soft and hard breaks, nested ordered and unordered lists with preserved starting numbers, task checkboxes, nested block quotes with a left rule, thematic rules, fenced/indented code, links, images as labeled host intents, and GFM tables with column alignment. Wide tables and code blocks scroll horizontally; short tables fill the available width. Task checkboxes reflect the document and do not mutate it. Code remains literal selectable text, now colored by the pinned offline highlighter described below; the document initializer accepts a `codeContent(language, source) -> AttributedString` closure for host-provided syntax coloring. No partial handwritten lexer is substituted for a real language highlighter. Source remains available unchanged for whole-response copying.

`MarkdownAction` delivers `openLink`, `image`, `copyCode`, `expandCode`, and `unsupported` events. The reusable UI performs no clipboard write, browser navigation, image download, or network request. For Markdown actions, the demo handles code-copy by writing its synthetic text to the pasteboard. Session messages forward these events through `.markdown(messageID, action)`; artifacts forward `.markdown(action)`.

For a paragraph containing only an image, hosts may provide `imageContent`; otherwise image alt text is presented inline as a tappable image intent. Hosts may provide `unsupportedContent` for explicit unsupported nodes. Raw HTML is literal text, never executed or interpreted as a web view. LaTeX math and footnotes are not added as a custom parser dialect: normal CommonMark interpretation applies, and hosts can construct `.unsupported(kind: .math/.footnote, source:)` nodes for their own renderers. This does not claim full mathematics, citation, footnote, remote-image, all-language syntax-coloring, or proprietary Claude artifact parity.

Native SwiftUI text selection is enabled per rendered text block/cell; continuous selection across separate blocks is not implemented. The original Markdown remains available through the existing response Copy intent. Dynamic Type fonts are used, but full accessibility-size visual parity and streaming performance under very large documents remain unmeasured.

Launch the demo with `--markdown` (optionally `--light`) to inspect synthetic formatting. The fixture exists only in `Demo/MarkdownFixture.swift`; no private conversation is embedded in the package. Semantic tests cover nesting, escaping, list starting indices/task state, code whitespace and an unclosed streaming fence, table alignment/missing cells, links/images/breaks, HTML fallback, explicit extension nodes, Unicode intent payloads, and empty input.

## Reference-driven syntax color refinement

The saved `claude-markdown-code-table.png` and `claude-expanded-code-viewer.png` establish colored Python tokens in both a code card and its expanded view. The observed purple keywords, blue function name, green string, yellow built-in type and red interpolation are consistent with Atom One Dark; this is an inference from the captured palette, not evidence of the source app's internal library. The demo now uses a short synthetic Python example with the same syntax categories.

The default renderer uses [HighlighterSwift 3.1.0](https://github.com/smittytone/HighlighterSwift/tree/3.1.0), the maintained [Highlightr successor](https://github.com/raspu/Highlightr), with its bundled highlight.js 11.11.1. Source is passed as a JavaScript function argument to the bundled lexer, not evaluated as a program. Rendering does not create a web view, issue network requests or fetch themes. The resulting native attributed text keeps only foreground color, so the existing SwiftUI font, selection, card geometry and copy intent remain authoritative. Host `codeContent` still takes precedence.

`ClaudeCodeHighlighter` is main-actor isolated, caches bounded immutable results separately for each theme, recognizes common language aliases, and falls back to the exact original text for missing/unknown languages, failed parsing, changed output text, or inputs over 100,000 UTF-16 code units. This size threshold is a conservative presentation safeguard, not a measured source-app limit. Lexer output is checked for exact source equality before it is accepted; no line numbers or inferred language are inserted. Upstream theme warnings for unstyled lexical categories use base styling and do not alter the source. The subsequently captured light Python reference confirms the same token categories on a white code card. Atom One Light remains an inferred approximation of those colors, not proof of the source app’s internal theme. Exact font metrics, whole-language coverage and very large streaming-document performance remain open.

## Captured light appearance and selectable inline-code refinement

The later `claude-markdown-code-table-light.png`, `claude-markdown-expanded-code-light.png`, and `claude-markdown-table-complete-light.png` establish a white code card over the warm near-white page, matching colored Python token categories, and a short three-column table that fits the transcript width. Code-card, inline-code and table-header backgrounds are independent theme values. The serif remains the licensed substitute, so exact font metrics are not claimed.

A native [SwiftUI Layout](https://developer.apple.com/documentation/swiftui/layout) measures cell content and allocates columns. Short columns share the viewport; unequal columns retain their measured widths when possible. Wider tables scroll, with long cells wrapping at the host-configurable column cap. This overflow policy is a conservative presentation choice, not a claim about uncaptured long-table behavior. Pure allocation tests cover short fit, unequal widths, wide overflow, long-cell caps, invalid geometry and empty input.

Paragraphs and table cells containing code use selectable UITextView text with a custom [NSLayoutManager background drawing hook](https://developer.apple.com/documentation/uikit/nslayoutmanager/drawbackground(forglyphrange:at:)). Rounded code pills draw behind native selection without inserting padding characters. Nested emphasis, blue code foreground, alignment and host link actions are retained. Plain paragraphs retain their existing SwiftUI presentation. The earlier TextRenderer limitation above is historical.

The composer’s static voice glyph is six unequal bars, measured in the saved light reference at visible pixel heights 9/19/33/19/28/9 with approximately 2× scale. This corrects an earlier five-bar visual impression. Actual speaking waveform reconstruction remains TODO by user request.
